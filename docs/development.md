# Разработка и диагностика

[← README](../README.md)

## Проверки без облака

```bash
npm ci
npm run typecheck
npm test
npm run build
```

Для этих проверок рабочая `.env`, токен, Terraform state и облачная инфраструктура не нужны. Локальные тесты используют синтетические данные Telegram и подменяют сетевые вызовы бота и Worker. `npm test` предварительно компилирует API, чтобы проверить настоящий YC HTTP-адаптер.

Сборка создаёт `apps/*/dist` и архивы `build/api.zip`, `build/bot.zip`. Архив API содержит JS, manifests и lock-файл; зависимости устанавливает сборщик Cloud Functions. `node_modules` в архив не включается.

## GitHub Actions

Workflow [.github/workflows/ci.yml](../.github/workflows/ci.yml) запускается на `push` и `pull_request`. Он использует Node.js из [.nvmrc](../.nvmrc), выполняет `npm ci`, `npm run typecheck`, `npm test` и `npm run build`, имеет `contents: read`, timeout и concurrency. Облачные credentials, `secrets.*`, OIDC и deployment-шаги в workflow отсутствуют. Это проверка кода и сборки, а не развёртывание и не проверка живого стенда.

Для Terraform без облачных изменений можно отдельно выполнить `terraform -chdir=infra fmt -check` и `terraform -chdir=infra validate` после `init` с backend config; для последнего нужны state-бакет и S3 credentials. Локальные npm-проверки от них не зависят.

## Локальный фронтенд

```bash
npm run dev
```

Vite показывает интерфейс и направляет `/api/*` на `http://127.0.0.1:3000`. Эта команда не запускает NestJS. Готового локального API-сервера и режима фиктивной авторизации в проекте нет. Обычный браузер без Telegram `initData` показывает приглашение открыть приложение из бота.

Для проверки полного сценария используйте развёрнутый стенд и запуск из Telegram. Состояние экрана и автоматическая авторизация также проверяются в [web.test.ts](../tests/web.test.ts).

## Проверка развёрнутого стенда

```bash
npm run verify
```

Проверка использует `.env` и Terraform outputs. Проверяются HTML и assets через Gateway, приватность функций и S3, отсутствие доступа без авторизации, синтетический подписанный вход, сохранение в YDB, изоляция пользователей, повтор операции и параллельные изменения. Временные записи удаляются в `finally`.

Это не проверка внутри настоящего Telegram WebView: открытие по кнопке нужно проверить вручную.

## Типовые проблемы

| Симптом | Что проверить |
| --- | --- |
| `Missing ... in .env` | Файл в корне проекта, обязательные переменные, путь к JSON-ключу |
| `401` в Mini App | Запуск из Telegram, актуальность `initData`, совпадение токена бота и Lockbox, часы |
| `403` или ошибка IAM при развёртывании | Права deployer на ресурсы, назначение IAM и использование runtime-аккаунтов |
| `/start` не отвечает | Триггер, целевая функция, доступ к Lockbox, `TG_PROXY_BASE`, доступность Bot API |
| После пересоздания Gateway открывается старый URL | Отправить новый `/start`; старая кнопка содержит прежний адрес |
| Health отвечает, счётчик не работает | `YDB_CS`, миграции, права API runtime на базу |
| Прокси отвечает `429` | Лимиты Worker и Telegram; повторить после `Retry-After` |
| Сборщик CF отклоняет архив | Убедиться, что используется `npm run build` и внутрь не добавлен `node_modules` |

Не прикладывайте к issue полные URL Bot API с токеном, `.env`, `initData`, ключи и state. Cloud Logging в этом шаблоне не используется как условие работоспособности.
